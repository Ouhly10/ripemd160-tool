# أداة RIPEMD-160 على GPU (Docker + GitHub Actions)

## ما هذه الأداة بالضبط
كيرنل CUDA يحسب `RIPEMD160` لمدخل **ثابت الطول 32 بايت** (أي ناتج
`SHA256(pubkey)`) بأقصى استغلال ممكن لأنوية RTX 4090 (thread لكل مدخل،
لا اعتمادية بين الـthreads). الهدف الافتراضي المُضمّن هو hash160 لغز #71:
```
f6f5431d25bbf7b12e8add9af5e3475c44a0a5b8
```

## كيف تم التحقق من صحة المنطق (قبل أي تسليم)
1. نسخة C عادية (`ripemd160_ref.c`) اختُبرت مقابل 3 متجهات رسمية معروفة
   (`""`, `"abc"`, `"message digest"`) — تطابقت جميعها.
2. نسخة C مخصصة لمدخل 32 بايت بالضبط (`ripemd160_fixed32`) قورنت
   ببرمجيًا بالنسخة العامة على 5 مدخلات عشوائية — تطابق كامل.
3. كيرنل CUDA (`ripemd160.cu`) هو نقل **حرفي** لنفس الدوال والجداول —
   تم التحقق برمجيًا (diff تلقائي) أن كل جداول الثوابت (`RL/RR/SL/SR/KL/KR`)
   مطابقة 100% بين نسخة C المُختبرة وملف CUDA.
4. `main.cu` يشغّل **self-test إلزامي عند كل تشغيل** (قبل أي بحث فعلي):
   يحسب هاش مدخلين معروفين (32 صفر بايت، و32×`0xAA`) على الـGPU فعليًا
   ويقارنهما بالقيم الصحيحة المحسوبة على CPU. لو فشل التطابق، **يتوقف
   البرنامج فورًا برسالة خطأ** ولا يكمل أي بحث.

⚠️ **ملاحظة صادقة**: لم يُختبر هذا الكود فعليًا على GPU حقيقي في هذه
البيئة (لا تتوفر بطاقة NVIDIA هنا) — فقط منطقه الرياضي تم التحقق منه
بدقة على CPU كما فوق. self-test عند الإقلاع هو خط الدفاع الأخير الذي
يمنعك من الوثوق بنتائج كيرنل معطوب لو وُجد أي خطأ تجميع/تشغيل لم أستطع
رصده هنا. **لا تثق بأي "تطابق" يظهر قبل أن ترى رسالة `[self-test] PASSED`.**

## ما هذه الأداة **ليست** إياه
- لا تولّد مفاتيح عامة صالحة ضمن نطاق اللغز `2^70..2^71-1` — تحتاج لذلك
  طبقة EC (`gen_startpubkeys.py` + تدرّج `-sp` كما في الرسائل السابقة).
  المشغّل الحالي (`ripemd160_random_batch_kernel`) يولّد مدخلات **عشوائية
  بالكامل على GPU نفسه** (عبر `splitmix64`، بدون أي بيانات من CPU أو نقل
  عبر PCIe) لغرض **قياس الإنتاجية (Mhashes/s) فقط** — تشغيله بدون ربطه
  بمصدر `SHA256(pubkey)` حقيقي لن "يحل" اللغز حتى لو عمل بسرعة عالية.
  (النسخة الأولى كانت تولّد العشوائية عبر `rand()` على CPU ثم تنقلها عبر
  `cudaMemcpy` — هذا كان يبطئ القياس فعليًا أكثر من حساب الهاش نفسه؛ تم
  حذفه بالكامل، ولم يعد هناك أي نقل بيانات من CPU لكل دفعة).
- لا تتضمن SHA256 (الخطوة السابقة لـRIPEMD160). التكامل الكامل
  `EC point → SHA256 → RIPEMD160 → مقارنة` يتطلب دمج هذا الكيرنل مع
  محرك EC الموجود أصلًا في `Vanity.cpp`، أو كتابة كيرنل SHA256 مماثل
  (بنفس منهجية self-test) لإكمال السلسلة.

## البناء والتشغيل
```bash
docker build --build-arg CUDA_ARCH=sm_89 -t ripemd160-tool .
docker run --gpus all \
  -e TELEGRAM_BOT_TOKEN="123456:ABC-DEF..." \
  -e TELEGRAM_CHAT_ID="123456789" \
  ripemd160-tool f6f5431d25bbf7b12e8add9af5e3475c44a0a5b8 16777216 100
```
الوسائط: `<target_hash160_hex> <batch_size> <num_batches>`.

GitHub Actions (`.github/workflows/build.yml`) يبني الصورة وينشرها على
`ghcr.io/<owner>/ripemd160-tool:latest` تلقائيًا عند كل push — جاهزة
للسحب مباشرة على أي عامل vast.ai يدعم `--gpus all`.

## متغيرات البيئة (Telegram)
| المتغير | الوصف |
|---|---|
| `TELEGRAM_BOT_TOKEN` | توكن البوت من BotFather |
| `TELEGRAM_CHAT_ID` | معرّف المحادثة/القناة المستهدفة |

- إن لم تُضبط، الأداة تعمل بشكل طبيعي وتطبع تحذيرًا في اللوج فقط (لا تتوقف).
- يُرسل إشعار تلقائيًا في 3 حالات: (1) بدء التشغيل بعد نجاح self-test،
  (2) فشل self-test (توقف فوري — يُخبرك أن الجهاز معطوب قبل إهدار وقت
  إيجار GPU)، (3) أي تطابق hash160 — **يُرسل قبل أي معالجة أخرى**، بنفس
  أولوية `server.py` الحالي في `btc71-hunter` (لتفادي فقدان النتيجة لو
  أُوقف instance فجأة).
- الإرسال عبر استدعاء `curl` مباشرة (مثبّت في الصورة) بدل مكتبة C++،
  لتفادي تعقيد ربط مكتبات HTTPS داخل بناء CUDA.

## قالب (Template) vast.ai المناسب
لا يوجد قالب "جاهز" على vast.ai لصورة خاصة — تُنشئ قالبك الخاص:

1. **Templates → New Template** في لوحة vast.ai.
2. **Image path**: `ghcr.io/ouhly10/ripemd160-tool:latest` (أو الـdigest
   المحدد بعد كل بناء، بنفس عادتك الحالية في تثبيت الصورة بـsha256 بدل
   `:latest` لتفادي تشغيل نسخة قديمة عن طريق الخطأ).
3. إن كان المستودع/الحزمة على GHCR **خاصة (private)**: فعّل "Use SSH"
   أو أدخل بيانات تسجيل الدخول لـDocker Registry في إعدادات القالب
   (`docker login ghcr.io` بمستخدم/PAT عندك)، وإلا ستفشل vast.ai في سحب
   الصورة.
4. **GPU Filter**: اختر `RTX 4090` تحديدًا (تطابق `sm_89` في build-arg).
5. **Launch Mode**: بما أن هذه الأداة CLI بدون واجهة ويب (بعكس
   `server.py` سابقًا)، اختر **"Entrypoint"** (يشغّل `CMD` الموجود في
   Dockerfile تلقائيًا) بدل "Jupyter"/"SSH" — إلا إن أردت الدخول يدويًا
   لضبط وسائط مختلفة، فاختر "SSH" وشغّل الأمر بنفسك داخل الحاوية.
6. **Environment Variables** (قسم في نفس صفحة القالب): أضف
   `TELEGRAM_BOT_TOKEN` و`TELEGRAM_CHAT_ID` هنا — تُمرَّر تلقائيًا كـ
   `-e` عند تشغيل الحاوية على أي instance تستأجره بهذا القالب، دون
   الحاجة لكتابتها يدويًا في كل مرة.
7. **Disk size**: صغير يكفي (الصورة CUDA devel + curl، لا بيانات كبيرة) —
   15-20GB كافية بفارق أمان.

بعد حفظ القالب: أي instance جديد تستأجره منه (RTX 4090) يسحب الصورة
ويشغّل الأداة تلقائيًا بمتغيرات Telegram جاهزة — تمامًا كتدفق العمل
الذي اعتدته مع `btc71-hunter`.

## الخطوة التالية المنطقية
لتكامل حقيقي (وليس قياس أداء فقط)، الخيار الأنسب هو **تعديل `Vanity.cpp`
نفسه** ليستدعي `ripemd160_fixed32` هنا بدل تطبيقه الداخلي (إن كان أبطأ)،
بدل بناء مسار بحث مستقل جديد — هذا يحافظ على منطق EC المُختبر مسبقًا
(`-sp`) ويضيف فقط تحسين هذه الخطوة بالذات.
